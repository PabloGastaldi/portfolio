## Purpose of This Design

Defines HOW the scaffold will be implemented. Locks the folder tree, dependency list, theming strategy, data shapes, and contact channel so the apply phase becomes a mechanical translation.

## 2. Dependencies (approved list)

Anything outside this list is rejected for the scaffold phase.

**runtime**
- `next` (15.x)
- `react`, `react-dom` (19.x)

**dev**
- `typescript` (5.x)
- `@types/react`, `@types/react-dom`, `@types/node`
- `tailwindcss` (3.x), `postcss`, `autoprefixer`
- `eslint`, `eslint-config-next`
- `prettier`, `prettier-plugin-tailwindcss`

**explicitly rejected for this change**

- `framer-motion`, `@radix-ui/*`, `lucide-react`, `clsx`, `class-variance-authority` — defer until a real need appears. Tailwind + template literals cover the scaffold.
- `react-hook-form`, `zod` — Contact form starts as `mailto:`; no client validation needed yet.
- `vitest`, `@testing-library/react`, `playwright` — deferred per proposal "Out of Scope".

## 3. Theme Toggle — Custom (no next-themes)

**Decision**: hand-rolled. Tailwind `darkMode: 'class'` + a small inline pre-paint script + a client `ThemeToggle` component.

**Rationale**: `next-themes` is ~5 kB gzipped and battle-tested, but the API surface we need is trivial (read system preference, persist choice, toggle `class` on `<html>`). Custom wins on the "no heavy deps" invariant and forces us to understand the FOUC mitigation we're shipping.

**FOUC mitigation**: in `src/app/layout.tsx`, render a `<script dangerouslySetInnerHTML>` inside `<head>` (BEFORE any styled markup) that:
1. Reads `localStorage.getItem('theme')`.
2. Falls back to `window.matchMedia('(prefers-color-scheme: dark)').matches`.
3. Adds `dark` class to `document.documentElement` synchronously.

Because this script is inline and runs before the browser paints body content, the correct theme class is on `<html>` before any CSS resolves — no flash. `ThemeToggle` is a `'use client'` component that mutates the same class and writes to `localStorage`.

**Storage key**: `pg-portfolio-theme`, values `'light' | 'dark' | 'system'`. Default on first visit: `'system'` (no key written until user toggles).

**Rejected alternatives**:
- `next-themes`: extra dep for ~5 kB, marginal value.
- CSS `prefers-color-scheme` only (no toggle): fails REQ-03-A (user can't switch).

## 4. Contact Channel — `mailto:` default, Formspree-ready

**Decision**: ship with `mailto:` as the wired path. Render a real form UI; on submit, build a `mailto:gastaldipablo1@gmail.com?subject=...&body=...` URL and `window.location.href = ...`.

**Rationale**:
- Zero external accounts to configure during scaffold (proposal explicitly allows `mailto:` fallback).
- Spec REQ-06-B accepts either form OR mailto.
- Form UI stays in place; swapping to Formspree later means changing one handler (`src/components/sections/Contact.tsx`) and adding the form action URL via env var. No structural change.

**Future Formspree swap path**: add `NEXT_PUBLIC_FORMSPREE_ENDPOINT` env var. If set, form posts there; if absent, falls back to `mailto:`. This branch lives in one place.

**Rejected alternatives**:
- Resend: requires a server route handler and API key management for what is currently zero traffic. Premature.
- Formspree as default: adds an external dependency Pablo hasn't signed up for; would block scaffold completion.

## 5. Data Layer Shapes

`src/types/content.ts`:

```ts
export type Pillar = 'data' | 'ai' | 'comex' | 'languages';

export interface Profile {
  name: string;
  tagline: string;          // positioning phrase (geopolitics + comex + data + AI)
  location: string;
  email: string;
  linkedin: string;
  languages: { name: string; level: string }[];
}

export interface Project {
  slug: string;             // stable id, used as key
  title: string;
  summary: string;          // 1-2 sentences
  description: string;      // longer body
  url?: string;             // external link
  repo?: string;            // optional repo url
  stack: string[];          // tech labels
  highlights: string[];     // bullet points (e.g. "RAG over NCM corpus")
  featured?: boolean;       // trade.ai = true
  order: number;            // ascending; lower = earlier
}

export interface Experience {
  slug: string;
  role: string;
  organization: string;
  location?: string;
  startDate: string;        // ISO yyyy-mm
  endDate?: string;         // ISO yyyy-mm, omitted = present
  summary: string;
  highlights: string[];
  order: number;            // ascending; lower = earlier in render
}

export interface Skill {
  name: string;
  pillar: Pillar;
  level?: 'basic' | 'intermediate' | 'advanced';
}
```

`src/data/*.ts` files export typed arrays (`Project[]`, `Experience[]`, `Skill[]`) and a single `profile: Profile` object. Each section component imports its array and renders it. Adding an item = appending an object literal.

Sorting rule: `Projects.tsx` and `Experience.tsx` sort by `order` ascending before render. `trade.ai` ships with `order: 0` and `featured: true`.

## 6. Styling Conventions

**Tailwind config**: `darkMode: 'class'`, content globs cover `src/**/*.{ts,tsx}`. Theme tokens are exposed via CSS custom properties in `globals.css` and referenced from `tailwind.config.ts` so colors swap by toggling the `dark` class.

```css
/* globals.css excerpt */
:root {
  --background: 0 0% 100%;
  --foreground: 222 47% 11%;
  --muted: 210 40% 96%;
  --accent: 221 83% 53%;
  --border: 214 32% 91%;
}
.dark {
  --background: 222 47% 6%;
  --foreground: 210 40% 98%;
  --muted: 217 33% 17%;
  --accent: 217 91% 60%;
  --border: 217 33% 20%;
}
```

Tailwind maps `bg-background`, `text-foreground`, etc. via `theme.extend.colors`.

**Fonts**: `Geist` and `Geist Mono` via `next/font/google` (zero runtime cost, self-hosted at build). Loaded once in `layout.tsx`, applied as CSS variables.

**Spacing**: Tailwind defaults. Container max-width: `max-w-5xl` (1024 px). Horizontal padding: `px-4 sm:px-6 lg:px-8`.

**Focus rings**: `focus-visible:ring-2 focus-visible:ring-accent focus-visible:ring-offset-2` on all interactive elements. Tap targets `min-h-11 min-w-11` (44 px) on mobile per REQ-04-B.

## 8. Performance

- No client-side data fetching. Site is pure SSG.
- `next/font` for fonts (no external font requests).
- `next/image` available but not required during scaffold (no real images yet); placeholder OG image is static.
- ThemeToggle is the only client component besides the form handler. Sections are server components by default.
- Bundle audit happens during apply (`next build` output inspected) per REQ-08-B.

## 9. Testing

**Decision**: defer entirely. No test runner, no example test, no scripts beyond `dev`, `build`, `start`, `lint`.

**Rationale**: proposal lists "Automated tests" as Out of Scope. Adding vitest + RTL now means choosing a config (jsdom vs happy-dom), wiring jest-dom matchers, and writing meaningless tests against placeholder components that will be rewritten when real content lands. A dedicated `testing-setup` change after real content is healthier.

**Verification of REQ-08-A**: handled by running `next build` during apply, no test runner needed.

## 10. Architectural Decisions (ADR-style)

### ADR-01: App Router over Pages Router
- **Context**: Two routing models exist in Next.js.
- **Decision**: App Router.
- **Rationale**: New default; server components reduce client bundle; better metadata API; this is a greenfield project with no legacy.
- **Rejected**: Pages Router — legacy mode, no reason to adopt new code there.

### ADR-02: Custom theme toggle, not next-themes
- See section 3.

### ADR-03: mailto default, Formspree-ready
- See section 4.

### ADR-04: Single-page, no routing
- **Context**: Sections could be separate routes (`/about`, `/projects`) or anchors on one page.
- **Decision**: single page, anchor scrolling.
- **Rationale**: Portfolio is short, recruiters scroll. Single page = better SEO concentration on one URL, simpler analytics later, faster perceived load. Spec REQ-01-B assumes anchor navigation.
- **Rejected**: multi-route — premature, adds nav complexity.

### ADR-05: No clsx / cva utility
- **Context**: Conditional classes will appear (theme toggle, active nav).
- **Decision**: use template literals and `Array.filter(Boolean).join(' ')` inline.
- **Rationale**: 3-5 occurrences total in scaffold. Adding a 2 kB util for this is over-engineering. If complexity grows, introduce `clsx` in a dedicated change.

### ADR-06: Tailwind tokens via CSS variables (HSL channels)
- **Context**: Two ways to do dark mode in Tailwind — `dark:` variant on every utility, or CSS variables swapped by `.dark` class.
- **Decision**: CSS variables.
- **Rationale**: One source of truth per token; component code stays theme-agnostic (`bg-background` not `bg-white dark:bg-zinc-900`). Easier to add a third theme later if ever needed.
- **Rejected**: `dark:` utility variants — doubles class noise, scatters theme decisions across components.

### ADR-07: Data files as TS modules, not JSON/MDX
- **Context**: Content could live in `.json`, `.ts`, `.md(x)`.
- **Decision**: TypeScript modules.
- **Rationale**: Type-checked at build time (REQ-02-B), supports comments/computed values, no parser needed. JSON loses types; MDX is overkill before there's a blog.
- **Rejected**: MDX — out of scope, no articles yet.

## 14. Risks and Assumptions

| Risk | Mitigation |
|---|---|
| Inline theme script CSP issues if a strict CSP is added later | Document that the script needs a hash or nonce if CSP is introduced. Not a scaffold concern. |
| `mailto:` UX is rough on desktop users without a mail client | Direct email and LinkedIn links are always visible alongside the form (REQ-06-A). |
| Tailwind v4 release mid-implementation | Pin to Tailwind 3.x in `package.json` to avoid mid-flight migration. |
| Next.js 15 minor changes | Pin to a specific 15.x version; bump deliberately in a later change. |
